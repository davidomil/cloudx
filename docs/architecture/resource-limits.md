# Resource limits

This audit accompanies issue #271. A user's retained history has no fixed
maximum size. Copy and migration paths must stream that history, check the
destination's available bytes and inodes, and preserve the source on failure.
Available capacity includes an applicable quota. Increasing a guessed history
maximum does not satisfy that contract.

Other limits bound work that CloudX materializes, parses, renders, or executes.
They are operational budgets, not measurements of a machine's physical capacity.
The values below record the current contracts. Tests establish the stated
behavior; they do not prove that each chosen value is optimal.

## Audit scope and method

The repository-wide discovery covered `apps`, `packages`, `services`, `scripts`,
`containers`, and `.github`. The review searched constants, parser/schema
constraints, subprocess buffers and deadlines, slices, retention, and pagination.
The discovery inventory contained 1,374 guard-pattern hits across 233 production
and configuration files, including references and false positives. Generated
dependency/build trees and test fixtures were excluded from that count. The tables identify the source
owners inspected and the regression files inspected. They group related guards
that protect the same allocation or lifecycle. They are not a claim that every
numeric literal or every vendored provider-schema field has a separate test.

Useful searches used for this audit:

```sh
rg --files apps packages services scripts containers .github
rg -n -i 'MAX_|max[A-Z]|max_|limit|timeout|deadline|bodyLimit|maxPayload|scrollback' apps packages services scripts containers .github
rg -n 'slice\(0, [0-9]|slice\(-[0-9]|maxLength|maxItems|maximum|le=' apps packages services scripts
```

Test files and fixtures were inspected as coverage evidence, not classified as
production admission limits. Layout coordinates, percentages, model dimensions,
identifier/hash lengths, protocol versions, and test fixture sizes are not
retained-data capacity policies.

Codex updates have no default aggregate or retained-state verification deadline. Explicit caller deadlines remain supported. Version lookup (10 seconds), registry lookup (30 seconds), and package installation (120 seconds) still stop unresponsive external commands. Synthetic native turns retain a 25-second liveness deadline. Verification progress is drained with an 8 KiB diagnostic tail instead of a lifetime output quota. `codex-updater.test.mjs` and `CodexUpdateService.test.ts` cover long progress, large progress output, explicit cancellation, process reaping, and preservation of the active selection.

Capacity probes inspect filesystem availability and user/group quotas. The existing probe reports project quotas as unavailable. Runtime ENOSPC/EDQUOT failures still stop copying and prevent activation; a preflight estimate cannot reserve against concurrent storage use.

Settings status and update-start helpers retain a 30-second control-request deadline. They inspect service metadata and active Forge ownership, not opaque retained histories. Interruption consent therefore does not hash conversation files. The detached update worker performs full recovery inspection and capacity checks, publishes scan progress, and repeats validation before marking the installation as mutating. Unsaved legacy tabs remain disclosed in the consent notice. `settings-update-recovery.test.mjs` exercises the production Settings caller with a valid 258 MiB transcript and an injected scan duration above 30 seconds; `managed-update-recovery-inspection.test.mjs` covers pre-stop failures, progress, and resume.

Terminal attachment verification has no aggregate 60-second deadline. Each broker acknowledgement still has a 10-second timeout, so checking more healthy sessions does not consume a fixed elapsed-time allowance.

Both internal snapshot helpers now return variable results in private files and a constant acknowledgement on stdout. Their callers and helpers must ship together. These internal CLI contracts changed; no compatibility path was added.

## Reproduce the large snapshot case

The regular suite skips the test that writes an 8 GiB-plus snapshot. Run it on a
disk-backed temporary filesystem with enough free capacity for that copy:

```sh
CLOUDX_LARGE_SNAPSHOT_TEST=1 TMPDIR=/tmp npx vitest run apps/server/src/plugins/CodexStateCompatibility.test.ts -t 'copies and verifies retained transcripts above 8 GiB' --maxWorkers=1
```

Use the regular tmpfs test setup for the other suites. The 10,001-file recovery
regression flushes every copied file; storage latency can dominate that case.

## Changes to future limits

Before adding or changing a bound:

1. Name the owner and the allocation, protocol, resource, or correctness failure.
2. Separate authoritative retained data from derived previews and diagnostic windows.
3. Use streaming or pagination for growing histories. Check actual capacity for copies.
4. Keep cancellation and progress active during large operations.
5. Add a boundary regression through the production path, including failure cleanup.
6. Make partial results explicit. Preserve authoritative source bytes on refusal.

The coverage references above record inspected tests. They do not claim that the
entire referenced suites ran for issue #271. The completion report records the
commands and observable outcomes actually validated for the committed change.
